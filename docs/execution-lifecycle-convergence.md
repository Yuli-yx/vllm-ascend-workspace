# 执行生命周期与更新事务收敛

状态：2026-10-15 架构审查与实现约束；修正尚未完成，不能作为验收通过记录。

后续复用审查与实机实验修正了两项实现选择：原生插件更新交给宿主管理器；
WSL 服务使用 systemd，macOS 的确证缺口使用最小共享 owner-pipe helper。
直接 API 在不具备已验证 OS 容器的边界复用同一 helper，不复制 Linux 版本。
最新责任和删除范围见
[原生更新、Hook 与进程管理复用](native-runtime-reuse.md)。
本文保留反例和必须兑现的结果语义，不要求继续保留自研更新器。

初始审查源码为 knowledge `61e1d99`、Codex `cf9a90a`、CC `c92e509`；
冻结的既有共享知识运行时为 `2fd20fe`，没有原地改写。后续代码重构在
源码工作树进行，最终版本和六组合验收必须重新绑定，不能沿用初始 SHA 声称通过。
CC 的额外 Windows owner HANDLE 草稿已保存并精确撤回，未提交或部署。
本文适用于后续版本和适配器，不包含 `0.0.1` 专用运行分支。

## 结论

共享知识组件、原生适配器和独立服务的总体分工应保留。当前的问题是
不同层重复解释所有权、完成和恢复条件，且解释已经发生漂移。需要减少
决策来源，不能用更多句柄、祖先进程扫描、状态文件或重试补偿这些冲突。

这次审查发现三个 P1 和一个 P2。前两个生命周期问题有真实无模型进程
实验，更新器问题由实际函数的故障注入证明状态转换可达。后者不是一次
已经观察到的原生安装覆盖事故。

## 已确认的问题

| 级别 | 触发及实际行为 | 实现位置 | 必须修正的边界 |
| --- | --- | --- | --- |
| P1 | Windows venv 在 core 与实际 worker 间增加启动进程。core 存活、worker 属于精确 Job，CC 仍误报 `native_owner_exited`，模型未启动 | CC `scripts/bounded.py:118,134,798`；共享 `loop/summary_scratch.py:54` | 托管摘要归属在共享边界验证，Windows 不再用适配器直接父 PID 重判 |
| P1 | macOS 托管摘要的 core 被 SIGKILL 后，CC worker 检出 owner 退出并结束直接 native，孙进程仍继续写；局部回执却为 `cleanup_failed=false` | CC `scripts/bounded.py:278`；`tests/test_maintenance_group.py:37` 只覆盖正常 cancel | owner 突然死亡必须终止整个自有操作树，不能再把清理委托给已经死亡的 core |
| P1 | 原生安装异常携带 `terminate_owned_tree` 失败，一次目标回读匹配仍被升为 `verified`；切换指针和后续回滚可继续 | CC `scripts/updater.py:845,856,903,927` | 分开保存已观察到的安装效果与写入者是否全部结束 |
| P2 | 保存的安装结果为 unknown 时，check 和 recover 都在只读对账之前直接退出 | CC `scripts/updater.py:1568,1894` | 禁止重放不等于禁止核对；已有恢复入口必须能只读收敛原操作 |

Windows 原自然 Stop 没有记录 worker PPID；不能补造原任务的进程快照。
独立复现使用同一安装字节，证明 core 活着、精确 Job 校验通过而 PPID
检查拒绝。macOS 实验则等待 worker/native/孙进程就绪后强杀 core，
确认其 finally 未执行，观察到孙进程继续写入，最后精确清理测试进程组。
以上均没有调用模型或重放失败任务。

更新器故障注入得到 `verified + cleanup_failed=true`，并确认 force
恢复对 unknown 的 `_readback` 调用次数为零。Codex 已在
`auto_update.py:998` 区分部分相应事实，可复用其语义和反例，但不能
因为另一端已有实现就省略对最终改动的验证。

## 需要保留的机制

| 对象 | 唯一责任边界 | 保留理由 |
| --- | --- | --- |
| 前台工具、安装与更新子操作 | 原生调用者拥有本次子树；安装前有独立的 stdlib 启动路径 | 调用者取消或退出后不能遗留写入者；尚未安装时不能反向依赖知识运行时 |
| 独立后台服务 | 共享组件管理服务身份、认证、消费锁、启动及精确退役 | 已准入的 Stop 需要在短宿主退出后继续消费；服务寿命不同于前台命令 |
| 一次摘要操作 | 共享执行边界拥有完整 worker/native 树和 scratch | 避免进程尚在写入时删除目录；适配器不能自行返回任意清理路径 |
| 原生协议 | 适配器负责命令、输出解析、原生终态和 usage 投影 | Codex JSONL 与 Claude JSON 不是同一协议，不应强行统一解析器 |
| 未决外部效果 | 现有 intent/receipt | 已发生的修改与 unknown 必须保留；不据此要求新架构继续自主管理 native 插件选择 |
| 诊断 | 已有安全字段、脱敏与独立上报选择 | 诊断记录不得改变业务结果，不能因上报失败重做模型或安装 |

这些是不同资源或效果的边界，文件数量不是删除依据。状态展示由权威
回执派生，不能成为第二个决定是否执行、回滚或重试的状态机。远端持久
job 的独立寿命也不改变，不能套用本地摘要结束即清理的规则。

## 进程所有权的收敛决定

Windows 保留 core 已有的 suspended spawn、精确 named Job 和
kill-on-close；共享 `create_profile` 验证托管摘要的声明和实际归属。
删除 CC 对这份归属的 PPID 重判，不采纳额外 owner HANDLE、进程创建
时间和新错误协议。验证失败仍须在 native 启动前显式拒绝。

不能把所有出现 `MINDIE_MAINTENANCE_GROUP` 的子命令都当成摘要。
现有只读 worker identity 和系统宿主辅助命令可以没有 scratch；只有
需要摘要临时 profile 的入口使用该完整合同。普通独立 bounded 调用
仍拥有自己的子树，不借用不存在的摘要 owner。

POSIX 必须补齐突然死亡保护。现有直接父 PID 轮询不能单独构成承诺；
CC 的实机反例已经证明“发现死亡”和“回收整个树”是两件事。先前未经
对照就选 guardian 的决定曾撤回；现已完成平台实验，再按确证缺口选择：

- WSL systemd 255.4 的真实无模型 main-death 实验已覆盖 worker 仍活着和
  已退出两种窗口，独立 PGID 后代均被 cgroup 回收，无自动重启。
- macOS launchd 对同 PGID 的清理通过，但 core 死亡不会回收另建 session
  的 writer，逐操作 job 也不会随独立 core 退出。选择最小共享 helper：
  core 唯一 pipe 写端、同组 watcher、exec 保持原进程身份，无业务状态或重试。
- 任何方案都要覆盖 worker 已退出、后代仍在运行而 core 随后死亡的窗口。
  适配器里的 `killpg(self)` 或正常取消库不能独自承担这个承诺。

平台缺口只在共享执行边界增加最小实现，不让每个适配器
各写一套。launcher 的创建成功不等于 worker 已执行；失败仍分别保留
未开始、已开始及未知，不能因换用平台工具丢失这份区分。

保持结果先持久化、正常取消和清理次序。只有共享保障完成反例验证后，
才能删除适配器旧保护；不能先全局关闭检查，也不能把仅补 CC 的
killpg 分支写成已经完成跨适配器收敛。

适配器内层 Job 暂时保留：它管理单次 native 输出、终态后的管道持有者
和局部取消，外层 core Job 管理整个摘要操作，两者作用域不同。删除
内层 Job 必须证明由哪一处接管这些职责，不能与本次错误 owner 判断
捆绑删除。

core 骤死可能留下私有 scratch，现合同不承诺崩溃后目录自动回收。
残留静态目录和仍在写入的孤儿进程分别记录；不为消除残留目录另建常驻
清理服务或扫描用户目录。

## 已有更新回执与迁移约束

原生更新机制已覆盖插件安装与选择，目标是迁移分发入口并删除重复
更新编排。以下语义用于解释现有未决操作和保留的服务交接，不是继续
扩建两个自研 updater 的任务清单。native 缓存与长寿命运行时的边界、
旧会话再次触发 Hook 和正式版本锁定必须先验证。

在已有回执中区分两个事实：原生目标的精确回读，以及原操作是否已经
停止全部写入。字段可沿用现有 `observed_target`、`execution_settled`
语义，不增加第二本事务账本。

| 已观察事实 | 允许的转换 |
| --- | --- |
| 调用未开始，intent 也未成功保存 | 保持未执行，不声称安装发生 |
| 目标回读匹配，但原写入者未确认结束 | 保存匹配观察，整体仍 unknown；禁止提交稳定指针或并发回滚 |
| 写入者确认结束，目标回读匹配 | 允许确认安装并提交本地选择；次级记账/诊断错误独立报告 |
| 写入者确认结束，精确旧选择与字节均未变 | 记录未应用；不能仅凭一个版本字符串推断 |
| 读取失败、身份不足或新旧均不匹配 | 保持原 unknown 和操作身份；不得以新安装覆盖它 |

`cleanup_failed` 一个总布尔值不足以判断是否仍有写入者。终止或 reap
失败与已经确认树退出后的管道关闭/诊断失败要分开；后者不能抹去已知
安装成功。现有 check/recover 在既有切换锁内先对账，核对原包、
版本和源码身份，不重新调用 install，不清除 unknown 以解除阻塞。
恢复仍缺证据时继续报告原操作未决，不能伪造收敛。

原生安装命令和插件缓存布局交给宿主。MindIE 保留精确 runtime identity、
状态兼容、服务交接和已有 unknown 的只读核对；不新建通用 updater
框架、服务或数据库，也不能通过删除账本伪造原未知操作已完成。

## 可维护性与验收顺序

先验证成熟机制的替代边界，再删除重复实现；不能先修完所有自研状态机
才考虑复用。安装前启动路径、原生协议解析和独立服务不能为了统一而
互相依赖。是否抽取以能删除多少独立判断为依据，不以模块行数或
“通用化”本身为目标。

跨适配器的验收应调用同一组行为反例，而不是各自模拟实现里的 flag：

1. 真实 Windows venv 间层合法启动，foreign/missing 摘要声明在 native
   之前拒绝；core 强制退出后 worker/native/持有管道的后代均结束。
2. POSIX 在 native 启动前、运行中以及终态交付附近强制结束 core；
   没有继续运行的操作树，没有伪造 usage，也没有自动重做模型。
3. 完成结果先记账，后关闭完整写入树和管道，最后删除自有 scratch；
   任一步失败保留已知结果和原错误。
4. 原生安装回读匹配但写入树未决时不切换、不回滚；后续已有 recover
   能只读确认已应用、未应用或仍未知，不重放原操作。
5. 安装前独立调用和独立服务仍分别符合自己的寿命；测试所用 watchdog
   不成为产品业务时限。

先用无模型真实进程和故障注入验证这些反例，闭环后再运行受影响的原生
采集。复用未变 query/explain、正文、已知用量和服务证据；共享执行边界
变化时补相关的两端操作树验证，不机械重跑所有付费回合。WSL 仍独立
验证 Linux 入口及服务，不能用 macOS 结果替代。

原始反例、平台选择与部分定向测试已完成，重复 updater 的删除、最终依赖锁
和六组合验收尚未全部完成。四项发现只有在替代路径和迁移证据齐全后才关闭；
发布继续阻塞，进展见 [0.0.1 准备](releases/0.0.1.md)。

## 九条原则审查

依据设计原则 blob `47c4407495e2c7421d16d05e8a094ce11f384c3b`：

1. 总成本：删除冲突的 owner 判断，先用无模型反例定位，避免付费试错。
2. 封闭问题：只收敛进程归属和效果确认，不抽象整个开发/发布流程。
3. 理解负担：无新增用户参数、恢复口令或日常管理步骤。
4. 单一边界：宿主管插件选择，包工具管依赖，共享层管业务交接，适配器管协议。
5. Skill 信息性：不增加强制 Skill 路线或用户收尾流程。
6. 知识参考性：实机复现和故障注入分别注明范围，不把审查当作已验收。
7. 按需介入：边界实验零模型、零重放；新客户端和验证环境使用任务独立目录，
   不原地更改既有运行时或全局业务配置。
8. 成果复用：优先原生 marketplace、uv 和 OS 管理机制；保留有效 Job、
   scratch、原生解析与既有证据；仅在已证实 OS 缺口处采用共享 helper。
9. 错误可见：列出误判、漏清理、过早确认及无法恢复，分别保留事实；
   没有用架构文档、草稿撤回或局部正常路径掩盖仍未修复的问题。
