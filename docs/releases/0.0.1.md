## 当前诊断与发布决定

2026-10-15 用户明确：耗时不是降低问题分析深度或发布要求的理由。
发布期间暴露的问题需要系统性归因；必要时重构或调整设计，不能把删除
超时当成性能问题已解决，也不能把 Windows 原生自动采集失效留作普通
已知限制。此前因约 17 小时耗时而停止根因排查的决定已撤销。

已确认 Codex Windows 原始业务 Stop 已入队但未形成材料/索引，消费者
原因仍需查清；后续另一诊断 Stop 中，同一 transcript 的扩展路径写法
被错误判断为越过 profile。旧验收把摘要尝试数误称为采集数，现已纠正
“完全没有采集”的推论。Claude Code Windows 的短 helper 会在
退出时清理仍需工作的后台服务。针对这些原因修正路径身份、服务归属和
共享生命周期；主任务同时复盘跨层合同、平台边界、错误交付和测试缺口。
同语料无采样对照已验证同步与初建索引存在可消除的重复计算，优化后的
实际业务仍超过 60 秒。细项见
[0.0.1 发布问题根因分析](0.0.1-root-cause-review.md)。
已付费和结果不确定的回合不重放，历史回执保留原版本边界。新的受控
复现与实机验证必须对应明确假设；既有未变代码的有效证据继续复用。

Windows SSH 修正已通过真实短命令和目录读取；两个产品已固定共同依赖
并推送官方仓库。四组合最终验收、测试准备、组件检查与 Release 发布
分别记录。仍未查明或未修复的核心问题保持阻塞，不能用 CI 通过代替。
已准备的原生捕获仅针对独立合成仓库；发布验证使用本地 bare Git 目标，
不能用它证明真实 GitHub PR、合并或公开 Issue 投递。

自动上报的真实 launchd / Task Scheduler 生命周期与本地 HTTP 投递已通过，
详情见下文。公开写入次数仍为 0，四组合最终原生验收尚未完成，
所有准备 PR 均待合入，`v0.0.1` 尚未创建。

## 设计原则 Review

依据产品原则提交 `6a81b410301a1791dcefa1f2b005b84bd853f720`。

1. 总成本：复用普通 Release 和现有安装器，benchmark 独立；不增加 beta 通道。
2. 封闭问题：版本读取、状态声明和候选检查限定在机械交付问题；实际收益不作机械保证。
3. 理解负担：用户只面对 `0.0.1`；内部安装标识与组件编号不形成新操作流程。
4. 单一边界：适配器负责原生打包，共享组件负责状态；此文档不增加运行时或依赖权威。
5. Skill 信息性：本次未增加强制 Skill 流程，发布文档不要求每个业务任务执行检查。
6. 知识参考性：公开发布、索引和检索不等于正确性或收益认证；限制保留。
7. 按需介入：验证仅在已授权的隔离合成任务范围启用贡献，不扩大到用户真实
   项目；不运行 benchmark 模型调用，不把本地模拟投递视为公开写入授权。
8. 成果复用：复用已有状态边界、安装器、固定组件及测试；仅扩展受影响检查。
9. 错误可见：缺失/错误候选版本拒绝打包；不同已发布格式拒绝重置；
   执行结果不确定仍保留。未完成的 Claude Code、Windows 和原生验收明确列出。
