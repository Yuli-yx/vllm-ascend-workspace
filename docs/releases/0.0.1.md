## 系统性修复与证据边界

本次按现象、直接原因、系统原因、修复及验证五层闭环；用户明确耗时不是
降低质量要求的理由。完整因果、原始失败和中间候选见
[发布问题根因分析](0.0.1-root-cause-review.md)。
最新架构决定见[执行生命周期与更新事务收敛](../execution-lifecycle-convergence.md)：
并由[原生更新、Hook 与进程管理复用](../native-runtime-reuse.md)修正实现路线：
先证明 native marketplace、锁定环境及 OS 管理机制能替代哪些自研职责，
删除重复编排并关闭现有反例后，再恢复受影响的原生验收。Codex 原生会
回收旧插件缓存，不能将“支持自动更新”写成“旧会话已安全通过”。
原审查的三个 P1 和一个 P2 仍须由最终实现和对应证据关闭；部分生产路径
已被删除或替换，不能继续把旧 updater 逻辑写成当前方案，也不能仅凭删掉
文件就关闭旧 unknown 的保留要求。保留事实不要求继续分发旧迁移器。

| 类别 | 确认的问题与结构性处理 |
| --- | --- |

## 发行准备与环境

- 产品 manifest 与原生 marketplace 使用 `0.0.1`；相同 release 不能覆盖
  不同字节。稳定入口使用明确 release，runtime 身份由源码、完整依赖锁、
  ABI 和平台组成；不再由自研 generation/current 选择代码。
- 知识和远端状态声明发布格式边界。同格式保留正文、游标、已付费结果、
  已执行及 unknown 请求；不兼容格式需显式迁移，不能重置为首次使用。
- 每个插件 Release 声明 Harness 版本区间和实际使用的接口；共享成熟 SemVer
  选择最高兼容正式版，原生安装器处理固定来源与安装记录。距离上次成功检查
  超过 24 小时后由自然使用异步触发；热路径只做轻量本地判断，失败独立退避，
  准备好的候选不重复下载或等待下一检查周期。后台准备，空闲时
  短暂切换；不征求同意、不通知、不要求 reload，既有授权不变。删除旧多阶段
  updater，不再追踪能绕过兼容筛选的无条件 latest。详见
  [发布兼容与静默更新](../release-compatibility-and-update.md)。
- 组件由各自官方仓库提供，适配器固定 revision。此前组件 main 与产品
  pin 不同来自合入/交付进度差异；发布需固定同一组合，不用“安装最新
  main”替代 Release。组件包版本与存储 FORMAT 不为统一显示而重编号。
- Windows Claude Code `2.1.299` 的 Flash 路由、`bypassPermissions`、实际
  Write/Bash 已验证；Windows Codex `0.162.0-alpha.17.2` 使用 Luna 完成
  真实请求。Mac Codex 为 `0.153.4`，Mac CC 为 `2.1.269`。
- 模型路由及全部权限是本轮用户指定的私有验证配置，不作为所有用户默认值。
  测试使用隔离合成项目，公开知识/Issue 写入尚未发生；SSH 和凭据只在本地
  操作文档及私有配置中保留。
- K3/Grok 并行产出已集成审查，其网关 HTTP 408 及用量保留；会话运行或
  结束不等于交付。当前三个既有子任务继续分别处理 Windows、CC 和独立审查。

最初原生 Windows 测试机的 WSL、Virtual Machine Platform 均 Disabled，
当前用户无发行版。用户随后指定改用另一台已有 WSL 的 Windows 主机，
因此未启用原主机系统功能，也未重启。新目标已只读核对 Ubuntu-24.04、
WSL2、ext4 home、Linux Python/Git 及 systemd；原盘点范围内未发现原生
Codex/CC CLI，现已在独立任务目录安装并验证官方 Linux 包。源码/SQLite/材料使用任务自己的 Linux 文件系统，
不改变默认发行版或已有业务。原生 Windows 与 WSL 的结果分别记录。

## 设计原则 Review

依据同提交的[产品设计原则](../design-principles.md)，包括 Harness 兼容最高
版本、成功检查间隔 24 小时、异步准备和空闲短切换约束。此处是发布文档
的 review，不能代替各实现最终 diff 及六组合验收。

1. 总成本：复用原生市场、uv 和 OS 管理机制，删除重复更新编排；更新热路径不联网、不反复扫描安装，失败退避；benchmark 独立，不增加 beta 通道。
2. 封闭问题：版本读取、状态声明和候选检查限定在机械交付问题；实际收益不作机械保证。
3. 理解负担：用户只面对 `0.0.1`；内部安装标识与组件编号不形成新操作流程，正常更新和重载不重新授权。
4. 单一边界：共享函数负责兼容选择，原生安装器负责下载和记录，一份安装配置负责活动绑定；不增加第二版本权威。
5. Skill 信息性：本次未增加强制 Skill 流程，发布文档不要求每个业务任务执行检查。
6. 知识参考性：公开发布、索引和检索不等于正确性或收益认证；限制保留。
7. 按需介入：验证仅在已授权的隔离合成任务范围启用贡献，不扩大到用户真实
   项目；不运行 benchmark 模型调用，不把本地模拟投递视为公开写入授权。
8. 机制与成果复用：先验证旧缓存、短 Hook 和平台所有权的确证缺口，再补稳定入口和最小 helper；删除未发布多代兼容及迁移链，Release 排序仅用于兼容选择；保留未变化的有效证据，不以历史通过冒充新组合通过。
9. 错误可见：缺失/错误候选版本拒绝打包；不同已发布格式拒绝重置；
   执行结果不确定仍保留。原生、CI、本地发布、公开送达与未完成门禁分列，
   已完成结果不因次级诊断或清理失败而被覆盖。
