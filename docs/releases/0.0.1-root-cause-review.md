# 0.0.1 发布问题根因分析

状态：调查中，2026-10-15。本文记录确认的因果与待验证假设，不代表
发布通过。候选、平台矩阵及证据边界见 [0.0.1](0.0.1.md)。

## 判断标准

用户要求妥善解决发布中暴露的问题，允许必要的重构和设计调整。总耗时
不是降低质量要求的依据。分析区分四层：

1. 现象：用户实际得到的结果、失效阶段和数据影响。
2. 直接原因：以具体调用、事件、源码和回执说明如何造成该现象。
3. 系统原因：为什么设计、职责划分、测试或交付机制没有提前阻止它。
4. 闭环：修复原因、相邻同类路径、验证实际产品行为并保留原失败证据。

单次运行超过 60 秒只证明耗时超过阈值。它不能证明业务合理地需要这么
久，也不能证明死锁。提高或取消阈值与消除低效、等待或生命周期故障
是不同工作，分别提供依据。

## 已作出的结构性调整

这次的问题不是一个统一的“Windows 慢”或“等待不够久”。当前按实际重复
缺陷收敛五个边界，不新增通用编排系统：

| 边界 | 之前的缺口 | 现在的责任和防回归要求 |
| --- | --- | --- |
| 服务所有权 | 短命 helper 启动后台消费，宿主退出即可终止；适配器又有较弱的存活快路 | core 统一启动、复用和退役；Windows 用按需系统宿主持有；每次复用核对配置指纹、active 与必要 worker；真实宿主退出后还须完成材料/索引 |
| 业务执行与资源清理 | 原生结果、用量、直接子进程退出及完整写入树混为一谈 | 已完成结果先落盘；core 管理自有 scratch 和完整树；明确区分活进程、僵尸与查询失败；清理故障不能抹去结果 |
| 时限与计算成本 | RPC、launcher、setup/update 各自设置业务总期限；多层重复验证和分词 | 沿实际调用链区分业务、连接、锁、清理和调用者取消；优化已证明的重复工作，保留必要校验，不用延长期限替代性能修复 |
| 外部操作与记账 | 记录失败或晚取消被当作操作未发生，可能重装、回滚或重做 | 写入前 intent；已完成、已失败和 unknown 独立保存；不确定先只读对账；后续记录/清理错误与原操作结果同时可见 |
| 验收与版本证据 | 用安装/存活/摘要数量推断采集成功，源码和 fixture 假设漂移 | 冻结源文件、宿主及共享依赖；逐 capture 核对材料、索引、用量和发布块；旧失败不改写；按变更影响复用证据，不因诊断或测试改动重复付费模型 |

2026-10-15 独立复盘又发现 CC `1fe695e` 的 `existing_service` 只检查
status RPC 是否返回，未验证选定配置指纹，也丢弃 worker 状态，且绕过
退役检查。`c96c319` 删除这条适配器快路，知识请求统一使用 core 的

worker-dead 和正常复用；19 项检查、8 subtests 通过，并经独立 diff
review。它说明统一启动入口还不够，所有复用入口必须服从同一个权威。

同轮 Windows `323a7af` 安装曾在候选校验返回
`publication_fetch/fetch_failed`。尚未执行 native install，也没有模型
调用、current 或 transaction。独立隔离诊断的 Git init、fetch、

execution/reason/returncode/cleanup_failed，不保存 argv、路径、自由文本
或凭据。未完成 spawn 不一律说成未执行，非零退出与清理失败同时保留。
每端 10 项新增检查及旧 reader 兼容检查通过，成功合同不变。
原失败回执保留；确认完整候选验证通过及无未决
原生写入后，只续接未完成的安装阶段，不重复 setup 或授权选择。

## 成熟机制复用与设计缺口验证

本轮复盘发现，先给每次故障追加局部保护，容易让两个适配器分别重做
进程 owner、版本选择和恢复判定。问题不在单个机制是否有用，而在相同资源
出现多个解释来源。原则 8 已更新：先验证宿主/OS/成熟组件的能力和确证缺口，
替代后实际删除重复实现；旧数据、授权和未决副作用仍由原权威记录保存。

| 问题 | 已核实的边界 | 收敛决定与验证范围 |
| --- | --- | --- |
| 原生自动更新能否直接替代私有 updater | Codex 0.153.4 原生更新会删除旧缓存，但旧会话甚至同 app-server 的新 thread 仍持有旧脚本路径；真实 Hook 返回 file-not-found | 使用固定 release 的数据目录入口和非 editable runtime；原生 fixture 已验证删除 v1 缓存后旧/新 thread 入口继续工作，新 app-server 选择 v2。无模型对照不代替最终自然 Stop |
| launchd 是否已经覆盖 core 突然退出 | 同 PGID 清理通过，独立 PGID 后代在 core 死后继续写；逐操作 launchd job 不随独立 core 死亡退出 | macOS 只在共享执行边界加最小 owner-pipe watcher，exec 保持身份，不增加业务状态、重试或独立 supervisor |
| Windows 和 WSL 是否仍需另一套 guardian | 真实 Windows named Job 和 WSL systemd 255.4 的两种窗口均回收后代，包括 worker 已先退出 | 保留 Job；WSL 服务采用 cgroup，不复制 guardian。普通直接 API 没有 OS 容器时复用同一共享 helper，并在执行前明确选择 |
| 是否需要旧 MCP/Stop 透明访问新服务 | 为尚未发布的代码构造兼容身份、successor 和版本排序，扩大了原缓存寿命缺口的处理范围 | 删除推测性多代兼容；一份安装绑定，常驻进程操作前核对，变化时明确要求重载；原生缓存寿命仍由稳定入口解决 |
| uv 是否会把 Hook 又变成安装器 | 即使业务 bootstrap 禁止准备，外层 `uv run --python` 仍可能下载解释器 | 安装/SessionStart 承担准备；Stop/PreTool 等短入口必须禁止下载/安装，未准备明确失败。锁、包检查和完成发布只在相应边界执行 |
| 短 Hook 唤醒是否仍被控制开销阻塞 | Scheduler 查询、ACL、注册、启动多次创建 PowerShell；曾测得 3.116 秒，超过 CC 1.5 秒内部/2 秒原生 Hook 预算 | 用已有 pywin32 直连同一系统 API，删除 PowerShell 传输；不提高业务期限、不依赖预热、不新增 broker。完整冷 Stop 及外层中断后的 unknown 仍须验证 |

三个原语实验、原生入口 fixture 和组件测试分别保留证据。六组合产品验收
必须绑定最终提交、完整依赖锁和本机宿主版本；不能用无模型 fixture 的 marker
冒充材料、索引、usage 或公开投递完成。旧已付费、失败和 unknown 回合不重放。

2026-10-15 曾在共享 `dbf6d7a` 中加入客户端兼容身份与 successor 路由，
并用三个合成版本测试忙 owner、跳过中间安装及迟到会话。实验确实发现
单个 retired 标记不能证明一个中间安装仍可接管，但它同时暴露了需求扩张：
原本需要解决的是缓存失效和服务归属，后来却在承诺未发布版本之间透明共存。
这些实验标签不是正式产品版本，测试通过也不构成保留该架构的理由。

用户明确可以破坏性重写未发布实现后，当前决定删除 `client_contract`、
后继路径与链遍历、版本比较、旧 updater 迁移及历史授权推断。只保留精确
安装和服务身份，普通入口不得改选 runtime。常驻 MCP 每次副作用前核对启动
身份，变化时明确要求重新加载。首次空 profile 初始化；已有不同绑定拒绝
覆盖，不实现替换事务。旧正文、usage、授权和 unknown 留在原处，不能借
删除代码重试付费调用或清空事实。最终六组合使用同一当前版本的首次和增量
自然 Stop，不再增加合成多代透明兼容门槛。

## 当前闭环状态

2026-10-15：当前源码、运行时和全部验收状态统一见发布文档开头，
下文“后续收敛”保留当时的检查点。`323a7af/2fd20fe` 的 Codex macOS
与原生 Windows 均已完成两次自然 Stop、首次/不重复增量、正文与索引、
已知用量、正常清理以及宿主退出后的持续消费。两平台同源码代际往返、
贡献停用、更新器停用/移除、精确退役和真实 native remove 通过。
Windows 精确核对实际服务 PID/创建时间、Scheduler 任务、认证连接及
consumer lock，不因缺失匹配项而空通过。

CC `c96c319/2fd20fe` 的 macOS 两次 capture-only 原生回合及摘要通过，
用量 1939/346、2094/433，均一次调用、清理正常。同源码 generation 往返、
精确退役、keep-data 原生卸载及业务状态/正文保留通过。新服务复用路径另用
实际 installed-adapter query/explain 验证；它不是模型触发的原生工具调用。
Windows CC 的 `c96c319` 实际冷 query 118.377 秒、explain 0.310 秒及
完整正文哈希通过，但自然 Stop 首次摘要失败为 `native_owner_exited`，
model_calls=0、billing=not_called、cleanup_failed=false；增量未执行。
源码发现 CC bounded 仍按直接 `getppid()==owner` 判断 Windows owner，
而 core 的 scratch 已因 venv redirector 改为精确 named Job 校验。
后续独立无模型实机复现已确认：core 存活、worker 位于精确 Job，
中间 venv 启动进程导致 CC 的 PPID 检查错误拒绝。原失败任务没有记录
worker PPID，不能将复现 PID 冒充原日志。失败回执保留，不重放。
额外 owner HANDLE 草稿已保存并精确撤回，选择复用共享 Job 合同。
所有同源码往返不声称跨版本迁移。

进一步架构审查发现同一责任漂移的另外三处：macOS managed CC 在
core 被 SIGKILL 后留下持续写入的孙进程，却记录 cleanup_failed=false；
CC 更新器接受“写入树清理失败 + 目标匹配快照”为 verified；保存的
unknown 在 check/recover 中又没有只读核对出口。第一项有真实无模型
进程反例，后两项为实际函数的故障注入，不能称已发生原生覆盖事故。
此前正常取消、正常退出和代际往返的成功不覆盖这些异常分支。

本轮确认三个 P1、一个 P2，均尚未修复。共享生命周期、原生协议、
安装前 bootstrap 和已有事务回执的保留/收敛决定统一记录在
[执行生命周期与更新事务收敛](../execution-lifecycle-convergence.md)，
不以新增句柄状态机或通用 updater 框架继续局部补丁。

随后针对成熟组件的审查确认，之前主要比较“如何修好已有自研代码”，
没有先核对原生能力，是设计调查顺序的问题。Codex/CC 已有原生插件
更新，当前 Codex 的 local marketplace 使其未走 Git 更新路径；
短 Hook 与独立持久 worker 也有成熟实践。因此撤回 POSIX guardian 的
预先选型，优先宿主更新、标准锁定环境和 OS 进程管理。
删除边界及 Codex 旧缓存回收、launchd 仅同 PGID 等限制见
[原生机制复用](../native-runtime-reuse.md)。这修正方案，不代表四项
缺陷已修复，也不抹去既有失败和付费/unknown 回执。

用户随后把 Windows WSL 的 Codex 与 CC 加入首发，六组合分别记录；
WSL 不能借用 PowerShell 或 macOS 的原生通过结论。已有成功回合不因此重放。
模型选择沿用原生 Windows，Linux 路径、进程与服务合同必须独立核对。

Lenovo 普通 TEMP 的定向用例通过；真实 GetShortPathName 返回的 8.3
TEMP 随后继续暴露同一 fixture 的项目根种子错误，cursor 断言已经通过，

Codex `323a7af` Windows CI 的真实 `bridge activate` 超过测试的 20 秒

该 component 用例将事先明确选择父测试进程持有的真实 service backend，

Scheduler 跨原生宿主生命周期则使用上述 Lenovo 原生结果。
选择发生在执行前，无失败 fallback，不改变产品实现或 timeout。
同时保留超时输出及只读启动诊断，清理不能吞掉原始错误或假装 owner 不存在。

## 2026-10-15 后续收敛

当前共享候选为 `2fd20fe980206c80dfa3fe586b1ee4c6f5c3e736`，
Codex 为 `323a7af57e70dcd6d351327f6ab2865fa4fe9714`，
CC 为 `1fe695e16dbfe6e6f1650cf4ec9b9a034b996e5a`；三个官方
PR 的 head 已回读一致。Mac 与 Lenovo 均新建独立运行时，核对三个
直接 Git 来源和 169 个包文件，全部字节匹配，依赖兼容性检查通过。
旧冻结环境保持原样。当前四组合原生验收仍在进行，安装成功不能提前
标成发布通过。

此检查点后 CC 追加了上述 `c96c319` 服务复用修复，knowledge/runtime
未变。Codex/macOS `323a7af` 已完成新的原生核心链路：两次自然 Stop
均在各自宿主退出后完成材料及索引；两次摘要用量为 11319/342、
11123/251 input/output tokens，均单次调用且 `cleanup_failed=false`。
完整原生动作、同流增量不重叠、逐 capture 材料/索引关联、完整 attempt
集合以及查询正文和本地发布哈希均通过。后续无模型的同源码代际切换、
兼容返回、贡献停用、更新器停用/移除及数据保留均通过；精确服务退役后，
实际宿主 `plugin remove` 和原生列表确认移除成功，共享数据仍在。
这不关闭跨版本迁移、自动 scheduler、fork/remote job 或真实 GitHub
送达，也不把其他组合的结果提前记为通过。

本轮的三个独立发现：

- **超时配置必须按实际版本和调用链核对。** Codex 的实际宿主
  `0.153.4`、`0.162.0-alpha.17.2` 官方 tag 源码都将 MCP 默认
  tool timeout 设为 300 秒、startup timeout 设为 30 秒。插件进入同一
  配置路径，模型调用没有传入更短期限。因此通用文档的 60 秒不能解释
  这两个版本的故障，也不据此修改 Codex 产品或安排付费延迟实验。
  这不推翻 CC 包装层真实 60,035 ms 截断的证据；两者是不同路径。
- **验收结果必须与逐条业务事实关联。** 旧验收除了漏读 captures，
  还可能忽略额外工具动作、以任意成功 region 代替所有 capture 完成，
  以及在最终 attempt 丢失时缩小发布要求。现已核查两轮完整原生事件流、
  每条合法材料回执及成功 region，通过 entry 和块集合关联新材料与
  完成索引，并固定第二轮完成时的 attempt 集合。27 项无模型反例及
  正常增量检查通过，独立复查通过；不改变旧回执或重跑旧模型。
- **失败状态真实，但原因不充分，仍是产品缺陷。** CC `e9b8a12` 的新
  Mac 原生冷查询、正文哈希和自然 Stop 已发生，首次摘要却收到原生
  `is_error=true`。用量已知，input/output 为 2353/710、cached 为 0，
  `cleanup_failed=false`；实际观察到共享私有 scratch 创建并删除。
  适配器此前丢弃原生失败 subtype，只保留通用 `native_turn_failed`，
  无法由现存回执区分轮次上限、结构化输出或后端失败。这一观测缺口
  必须修正，不能通过重放成功覆盖。增量回合未执行，原任务已精确退役；
  后续通过静态分类、安全元数据和无模型失败回归补齐调用者诊断。

CC 修正 `be34250` 已包含在官方候选：已确认的轮次上限、成本预算和结构化
输出耗尽使用不同静态原因，私有失败回执仅保存允许的 enum、数值和字段
形状，不保存自由文本、prompt、凭据或 session ID。34 项适配器检查及
5 subtests 通过，共享原因合同 11 项通过；原生非零退出不能覆盖先到达
的终态和已知用量。它修复可定位性，但不会补造旧失败已经丢失的 subtype。

前一候选的两端 macOS CI 同时在共享 `cleanup_failed` 断言失败。独立无模型
复现的诊断堆栈已定位到 SIGKILL/直接子进程回收后的 `killpg(pgid, 0)`
返回 EPERM；不是已经证明仍有活跃写入者，也不能直接当作进程不存在。
清理合同必须核实已无可写后代，区分活跃进程、僵尸记录、查询失败及目录
删除故障。同一自有进程组的确定性实验依次观察到：活进程可接受 signal 0，
未回收僵尸返回 EPERM，完成回收后返回 ESRCH。共享修正 `2fd20fe`
只在 signal 0 不能证明消失时检查 PID/PGID/state，按精确进程组过滤；
空组或全为合法僵尸状态才证明没有写入者。活进程、未知状态、解析或查询
失败仍报清理失败，不能把 EPERM 直接当作已退出。既有终止信号、直接
子进程回收及两秒观察边界保留，不影响 Windows 路径。

共享相关检查 45 passed、2 Windows skips；原来失败的 CC 和 Codex
真实进程 fixture 各单次通过，无模型调用。最新 CC `1fe695e` 的
完整 Adapter checks 和 knowledge `2fd20fe` 的 Package checks 已
在线回读成功；其余当前提交检查与最终原生清理结果分别追踪。

调查驱动还曾绕过 pytest 隔离入口，向默认诊断目录追加一条合成清理
事件。只读核对确认默认报告 policy、reporter state 和公开 outbox 均
不存在，没有公共投递；原事件未删除。后续驱动在启动前显式验证诊断路径
位于任务目录且 reporting off。测试隔离不能只依赖某一种测试收集入口。

以上分别属于宿主合同核对、验收正确性和产品错误交付，不汇总为同一个
“超时问题”。业务耗时分解、进程归属和原生全链路各有独立关闭条件。

## 已定位的因果链

Codex Windows 的新自然 Hook 对照证明 SessionStart、UserPromptSubmit、
Stop 可以执行，直接 Python 与产品 PowerShell 包装均成功。随后只在
任务自有安装中加诊断，观察到插件 Stop 正常进入原 launcher、授权与
payload 解析通过，采集 helper 在约 164 ms 内失败。原生路径使用
`\\?\` 扩展命名空间，而 profile 比较的另一端没有该前缀；同一文件
被误判越界。这是适配器的路径身份错误，不是宿主缺少 Stop 能力。

进一步逐表核对发现，原始业务回合实际已入队。旧验收脚本只检查
`material_summary_attempts`、streams、tasks、batches，没有检查 captures；
`capture_attempt_count` 实际保存的是摘要尝试数。旧观察结果保留，撤销
其“没有 capture”的解释，修正 snapshot 字段与逐阶段核对。后续路径
拒绝与原始 queued 是不同事件，必须分别分析。原 consumer.lock 记录曾
启动 PID 45044，但退役核对时已不持有锁；没有留下服务退出原因。
原队列不重放，新验收使用独立、更深的数据目录，保留旧数据和费用记录。

独立无模型 fixture 通过真实 Windows Codex 0.162.0-alpha.17.2
app-server 的 thread/start 和 MCP initialize 启动长活 marker，使用原
产品 service spawn 路径；原生宿主退出后 marker 心跳立即停止。进程
查询确认外层 Job 标志为 8192（KILL_ON_JOB_CLOSE），且没有允许
BREAKAWAY 或 SILENT_BREAKAWAY。该 Job 包含 MCP 的宿主祖先链。
这证明适配器自己的 helper 允许脱离，仍不足以跨越宿主所有权边界。
该实验未调用模型、未读取或重放原业务队列；它是机制复现，不是补造
原始事件的退出日志。

因此 Windows 知识服务需要明确独立于短宿主的所有者。当前设计方向为
复用系统 Task Scheduler 的按需服务宿主，不设周期或登录触发，不增加
常驻 broker。现有 consumer lock、认证 endpoint、worker readiness 和
精确 retirement 仍负责实际服务状态；任务登记或 Running 不算就绪。
共享候选已实现这一边界。新无模型实机实验经过真实 Codex app-server、
MCP、bounded helper 和 `cli.ensure_service`，取得认证 endpoint 的
`worker_alive=true`；宿主 exit 0 后仍可认证查询，consumer lock 继续持有。
实验同时用合成环境变量验证 MCP 声明、一次性上下文传输和 worker 初始化
的完整路径。随后精确 retirement 确认任务删除、consumer lock 释放。
这比单独 marker 存活多验证了实际 core 服务，但仍不是材料/索引验收。

同一测试进一步放到 392 字符的 manifest/XML 深路径，先暴露服务启动锁
仍使用普通路径的问题。共享锁、connection、retirement 和启动诊断文件
统一使用已有 Windows I/O 路径工具后，又定位到 Task Scheduler 的
`WorkingDirectory` schema 只允许 260 字符。保持 manifest、XML 和
权威数据目录不变，仅移除非必要的任务工作目录字段，真实服务就绪、
宿主退出后存活和精确退役再次通过。Python host 保留原启动工作目录
语义；不把迁移到短数据目录作为修复，也不把组件路径测试视为已覆盖
系统任务登记约束。

最终源码的另一独立实机 fixture 保留 395 字符 manifest 路径，并检查
服务内 cwd 与调用者一致。真实 Codex exit 0 后，认证 worker 和
consumer lock 均继续有效；一次性 DPAPI 上下文已消费删除，XML 不含
`WorkingDirectory`。精确退役后任务不存在、消费锁释放。它不调用模型，
也不读取原业务队列；仍须以最终安装上的自然 Stop 完成材料/索引验收。

安装配置只持久化选定原生 profile、可执行文件、诊断位置及允许传递的
环境变量名称。Windows 使用绑定 SID、配置指纹和 nonce 的短期 DPAPI
文件传递实际值，服务启动前消费并删除，不把凭据写入 Task XML 或引擎
配置。POSIX 也应用相同的安装路径声明，环境值沿原有继承路径传递。
凭据缺失由实际 provider 校验，关闭贡献时不要求无关的模型凭据。

审查继续区分系统管理 RPC 与服务业务寿命：Task Scheduler 管理请求保留
有限 IPC/输出边界；服务本身没有任意 60 秒总时限。Start 响应不确定时，
一次 idle 状态或未变化的 LastRunTime 不能证明它没执行，不允许据此再次
Start。清理阶段同样不能无限等待不确定的 manager 状态；静态错误阶段、
代码和不确定标记必须穿过 Hook/调用边界，不能再次压成不可定位的通用失败。

共享宿主的独立审查又复现并修正四条边界，保留修复前后证据：

- 调用者未提供某个声明变量时，后台环境中的旧值可能被继续使用。现在
  先按 Windows 名称大小写规则清除声明范围，再应用已验证的调用者值和
  固定路径；缺失仍为缺失，其他环境不变。
- 系统已接受 Start，但写入 `started` 回执失败时，原分支删除待消费的
  上下文并误报确定失败。现在保留启动 intent 和上下文，返回
  `start_receipt_write_failed / uncertain:true`；后续只核对同一 attempt，
  故障注入确认没有第二次 Start。
- Stop 的新启动路径曾锁定 `state-v1/start.lock`，查询和退役使用
  `domain/start.lock`，两把真实锁可同时取得。现在统一到既有共享锁；
  回归持有该锁时要求合并等待，不能调用 manager。
- 同一配置的 `\\?\` 写法在 `Path.resolve` 后仍保留前缀，但启动记录
  曾去掉前缀，改变了既有 fingerprint。Lenovo 只读实验证明它们指向
  同一文件却往返失败；记录现保留调用者 resolved spelling，不改现有
  指纹和退役协议，也不迁移历史状态。

这些修正说明“把服务放到 Scheduler”本身不够：还要保留调用者上下文、
共享互斥和真实操作结果。独立审查未发现额外高置信阻塞，但不替代最终
组件回归与原生材料验收。

CC Windows 使用实际 `d78b628` 的 bounded runner 复现服务归属。
在清理前持有服务真实 PID 的进程句柄：默认路径中服务从存活变为
Job cleanup 后退出；只为明确的服务启动允许脱离后，服务在 cleanup
后仍存活，正常 release 后以 0 退出；普通孙进程仍被 Job 终止。
这证明 Popen 成功不能代表已完成所有权转交。此实验只覆盖自己的
helper Job，严格外层 Job 是进一步发现的边界。它与冷索引耗时是两个
可叠加的问题，不能用其中一个解释掉另一个。

修正后的 Windows 小语料进程级 fixture 已完成两次真实 helper 查询，
耗时分别为 1.339 秒和 0.206 秒。两次使用同一服务 PID、endpoint 身份
哈希及 ReMe 对象；只发生一次 checkpoint load 和 material rebuild，
第二次没有重载或重建。共享 retirement 能停止服务并释放 consumer，
精确 receipt restore 通过。这证明进程所有权修正的效果，尚不能替代
660 条语料或真实 Claude Stop 的验收。

## 已确认的测试盲区

### 服务就绪、实际检索和完整清理是不同边界

Mac Codex `52966a9` 的新自然验收完成 query/explain、两个业务回合、

### 深路径验收不得悄悄扩大产品范围

已有 Lenovo 文档已经区分：正常 Git 仓库根下的 422 字符数据库、
390 字符 staging、281 字符正文、304 字符发布文件通过；Git 仓库根本身
达到 334 字符仍不受当前依赖支持。新验收 fixture 却把“保留深路径”
写成整个 DATA 根必须超过 260 字符，造成另一次不可用 feed。
这是验收约束扩大，不能当作原路径修复回归，也不能通过改短路径
宣称支持了原来不支持的 Git 根。

该失败保留在独立 profile，未调用模型。只读与本地 bare 对照分别确认
绝对 Git 根、扩展命名空间及深工作目录的依赖限制；`core.longpaths`
不消除这些边界。后续原生验收采用依赖支持的 Git 根，同时继续覆盖真实
深材料路径和扩展路径身份；transcript 是否超长按实际路径单独记录，
不把材料的长度当作 transcript 的证据。产品应在适用 Git 边界清楚报错，
不自动迁移数据或建立长期短路径别名。

`3851f58` 在共享 Git 边界增加只读 preflight：当前 Windows Git 的
实际 gitdir 限制为 220 UTF-8 bytes，工作树计入 `.git`，不是所有文件
路径统一限制为 220 字符。Feed 在创建缓存前检查，publication 在
clone/fetch 前检查；两个适配器在打开 Store 前调用同一检查。错误只带
安全 code、角色和长度，不输出私有路径。已有 unknown 发布的对账若被
该配置限制阻止，仍保留 unknown、head、PR 及已完成 push 步骤，不会
变成 not_started 并重发。Mac 22 项、Lenovo 14 项组件回归通过，
两端 prepare-store 入口各通过；全部八个相关文件与 Windows 测试清单
逐字节一致。最终安装验收尚待进行。

## 重构决定的依据

- 若耗时来自每次请求重新载入或构建完整语料，修正初始化和增量边界；
  不通过放大超时掩盖重复工作。
- 若耗时来自锁或 owner 生命周期错误，修正所有权、启动与取消传播；
  不启动第二个服务或增加自动重试绕过。
- 若工作本身持续推进且成本与材料量相符，修正任意业务总时限，
  同时保留调用者取消、连接故障和具体资源边界。
- 若宿主未派发或没有执行 Hook，修正宿主契约或安装适配；
  若命令已执行而后续丢失，修正对应解析、身份、授权或持久准入阶段。
  不用手动注入 Stop 宣称原生链路通过。
- 如果相同生命周期或平台规则由多个组件各自实现并已产生不同语义，
  优先收敛到其现有责任方。是否抽取共享实现由实际重复和依赖方向决定，
  不新增通用编排层、第二权威状态或日常用户操作。
