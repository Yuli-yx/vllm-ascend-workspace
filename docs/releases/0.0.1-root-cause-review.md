# 0.0.1 发布问题根因分析

状态：调查中，2026-10-16。本文记录确认的因果与待验证假设，不代表
发布通过。候选、平台矩阵及证据边界见 [0.0.1](0.0.1.md)。

## 判断标准

用户要求妥善解决发布中暴露的问题，允许必要的重构和设计调整。总耗时
不是降低质量要求的依据。分析区分四层：

1. 现象：用户实际得到的结果、失效阶段和数据影响。
2. 直接原因：以具体调用、事件、源码和回执说明如何造成该现象。
3. 系统原因：为什么设计、职责划分、测试或交付机制没有提前阻止它。
4. 闭环：修复原因、相邻同类路径、验证实际产品行为并保留原失败证据。

单次运行超过 60 秒只证明耗时超过阈值。它不能证明业务合理地需要这么
久，也不能证明死锁。提高或取消阈值与消除低效、等待或生命周期故障
是不同工作，分别提供依据。

## 已作出的结构性调整

这次的问题不是一个统一的“Windows 慢”或“等待不够久”。当前按实际重复
缺陷收敛五个边界，不新增通用编排系统：

| 边界 | 之前的缺口 | 现在的责任和防回归要求 |
| --- | --- | --- |
| 服务所有权 | 短命 helper 启动后台消费，宿主退出即可终止；适配器又有较弱的存活快路 | core 统一启动、复用和退役；Windows 用按需系统宿主持有；每次复用核对配置指纹、active 与必要 worker；真实宿主退出后还须完成材料/索引 |
| 业务执行与资源清理 | 原生结果、用量、直接子进程退出及完整写入树混为一谈 | 已完成结果先落盘；core 管理自有 scratch 和完整树；明确区分活进程、僵尸与查询失败；清理故障不能抹去结果 |
| 时限与计算成本 | RPC、launcher、setup/update 各自设置业务总期限；多层重复验证和分词 | 沿实际调用链区分业务、连接、锁、清理和调用者取消；优化已证明的重复工作，保留必要校验，不用延长期限替代性能修复 |
| 外部操作与记账 | 记录失败或晚取消被当作操作未发生，可能重装、回滚或重做 | 写入前 intent；已完成、已失败和 unknown 独立保存；不确定先只读对账；后续记录/清理错误与原操作结果同时可见 |
| 验收与版本证据 | 用安装/存活/摘要数量推断采集成功，源码和 fixture 假设漂移 | 冻结源文件、宿主及共享依赖；逐 capture 核对材料、索引、用量和发布块；旧失败不改写；按变更影响复用证据，不因诊断或测试改动重复付费模型 |

2026-10-15 独立复盘又发现 CC `1fe695e` 的 `existing_service` 只检查
status RPC 是否返回，未验证选定配置指纹，也丢弃 worker 状态，且绕过
退役检查。`c96c319` 删除这条适配器快路，知识请求统一使用 core 的
`ensure_service`；core 原有健康连接快路仍不重复启动。实际配置/连接/
退役文件及 OS 消费锁配合 transport 检查覆盖了错误指纹、retired、
worker-dead 和正常复用；19 项检查、8 subtests 通过，并经独立 diff
review。它说明统一启动入口还不够，所有复用入口必须服从同一个权威。

同轮 Windows `323a7af` 安装曾在候选校验返回
`publication_fetch/fetch_failed`。尚未执行 native install，也没有模型
调用、current 或 transaction。独立隔离诊断的 Git init、fetch、
rev-parse 及固定发布合同校验都成功；不能据此恢复原始失败原因，或宣称
网络故障已被修复。原校验把三个 Git 子步骤压成同一错误；Codex `a7b4090`
与 CC `c92e509` 已分开 init/fetch/revision-read，保留白名单
execution/reason/returncode/cleanup_failed，不保存 argv、路径、自由文本
或凭据。未完成 spawn 不一律说成未执行，非零退出与清理失败同时保留。
每端 10 项新增检查及旧 reader 兼容检查通过，成功合同不变。
原失败回执保留；确认完整候选验证通过及无未决
原生写入后，只续接未完成的安装阶段，不重复 setup 或授权选择。

## 成熟机制复用与设计缺口验证

本轮复盘发现，先给每次故障追加局部保护，容易让两个适配器分别重做
进程 owner、版本选择和恢复判定。问题不在单个机制是否有用，而在相同资源
出现多个解释来源。原则 8 已更新：先验证宿主/OS/成熟组件的能力和确证缺口，
替代后实际删除重复实现；旧数据、授权和未决副作用仍由原权威记录保存。

| 问题 | 已核实的边界 | 收敛决定与验证范围 |
| --- | --- | --- |
| 原生自动更新能否直接替代私有 updater | Codex 0.153.4 原生更新会删除旧缓存，但旧会话甚至同 app-server 的新 thread 仍持有旧脚本路径；真实 Hook 返回 file-not-found | 使用固定 release 的数据目录入口和非 editable runtime；原生 fixture 已验证删除旧缓存后旧/新 thread 入口继续工作，新 app-server 选择新安装。无模型对照不代替最终自然 Stop |
| launchd 是否已经覆盖 core 突然退出 | 同 PGID 清理通过，独立 PGID 后代在 core 死后继续写；逐操作 launchd job 不随独立 core 死亡退出 | macOS 只在共享执行边界加最小 owner-pipe watcher，exec 保持身份，不增加业务状态、重试或独立 supervisor |
| Windows 和 WSL 是否仍需另一套 guardian | 真实 Windows named Job 和 WSL systemd 255.4 的两种窗口均回收后代，包括 worker 已先退出 | 保留 Job；WSL 服务采用 cgroup，不复制 guardian。普通直接 API 没有 OS 容器时复用同一共享 helper，并在执行前明确选择 |
| 如何让更新保持简单且不破坏活动操作 | 原拒绝不同绑定只支持首次安装；多代兼容身份和 successor 又扩大了职责 | 按用户最新合同：稳定入口、一份 canonical 绑定、后台准备、忙时延期和空闲短切换；允许短暂不可用，不重新授权或要求 reload，不恢复多代路由 |
| uv 是否会把 Hook 又变成安装器 | 即使业务 bootstrap 禁止准备，外层 `uv run --python` 仍可能下载解释器 | 安装/SessionStart 承担准备；Stop/PreTool 等短入口必须禁止下载/安装，未准备明确失败。锁、包检查和完成发布只在相应边界执行 |
| 短 Hook 唤醒是否仍被控制开销阻塞 | Scheduler 查询、ACL、注册、启动多次创建 PowerShell；曾测得 3.116 秒，超过 CC 1.5 秒内部/2 秒原生 Hook 预算 | 用已有 pywin32 直连同一系统 API，删除 PowerShell 传输；不提高业务期限、不依赖预热、不新增 broker。完整冷 Stop 及外层中断后的 unknown 仍须验证 |

三个原语实验、原生入口 fixture 和组件测试分别保留证据。六组合产品验收
必须绑定最终提交、完整依赖锁和本机宿主版本；不能用无模型 fixture 的 marker
冒充材料、索引、usage 或公开投递完成。旧已付费、失败和 unknown 回合不重放。

2026-10-15 曾在共享 `dbf6d7a` 中加入客户端兼容身份与 successor 路由，
并用三个合成版本测试忙 owner、跳过中间安装及迟到会话。实验确实发现
单个 retired 标记不能证明一个中间安装仍可接管，但它同时暴露了需求扩张：
原本需要解决的是缓存失效和服务归属，后来却在承诺未发布版本之间透明共存。
这些实验标签不是正式产品版本，测试通过也不构成保留该架构的理由。

用户明确可以破坏性重写未发布实现后，已删除 `client_contract`、后继路径
与链遍历、旧 updater 迁移及历史授权推断。随后又明确更新应按 Harness 支持
区间选择最高正式 Release，静默准备和切换，允许相关接口短暂不可用。
因此“不同绑定一律拒绝、用户手动 reload”也不是最终合同。

当前收敛为原生安装器、共享纯版本选择、集中接口清单与一份 canonical 安装
绑定。业务共享准入锁，更新非阻塞尝试排他锁；空闲才切换，忙则延后。30 秒
只是控制阶段候选观察窗口，不作为业务上限。不会为此恢复多代兼容或后继链，
也不把版本大小当作实际 FORMAT 兼容证明。验证包括中断、启动失败、旧入口
恢复和原数据/授权保留，细节见[当前更新合同](../release-compatibility-and-update.md)。

### 静默更新集成暴露的边界

| 现象 | 直接原因与系统性缺口 | 处理与当前证据 |
| --- | --- | --- |
| 更新检查可能拖慢日常调用 | 网络发行选择、完整运行时校验和业务请求没有明确分频 | 以上次成功检查为准，每 24 小时后由自然使用异步触发；进程内轻量判断、失败退避、并发合并与准备后独立切换。两端未到期路径无网络/子进程，不能把局部触发耗时当成整体业务 benchmark |
| 安装命令已退出而下一阶段仍可能重复 | 原生安装、运行时准备及切换 helper 的完成事实不完全对称；上一条命令的 settled 不能证明下一条已结束 | 复用原有单次执行回执，在每个实际写入进程开始前清除旧完成事实；未决写入阻止重入，已知完成与记账失败分开。没有增加第二账本或通用事务管理器 |
| 新激活 helper 在原生双运行时实验中导入失败 | 实际调用使用 `python -I`，新脚本缺少现有入口采用的本目录导入设置；直接模块测试没有覆盖隔离子进程入口 | Codex `ea5cf6e` 修正入口并增加真实隔离解释器回归。原失败在退役及 canonical 写入前发生，已保存非零退出和成功清理，不伪称已经切换 |
| 切换窗口的 Stop 尚未入队就结束 | 将不会自动重发的短 Hook 与可返回暂不可用的 RPC 一起放在安装门禁之后，忽略了事件持久准入必须先完成 | CC 实际 raw launcher 在排他锁内约 1.601 秒返回 warning、captures 为空；两端应复用已有 capture 队列，将一次完整绑定快照的持久准入与服务唤醒分开。原生自然事件和新 owner 消费仍需验收，禁止仅测切换后的 Stop |
| Windows CI 没有进入预期故障阶段 | 退休测试用 100 毫秒全局时限，希望在真实 ACK 后超时，实际先在 ACK 前耗尽；墙钟假设代替了阶段条件 | 共享 `4076ac7` 仅修测试，在真实 ACK 和退休回执之后精确注入 consumer 等待超时。Mac/Lenovo 定向通过，产品源码 tree 不变，新 CI 单列，不扩大产品期限 |

这些问题分别属于频率、进程结果、真实入口、事件可靠性和测试注入边界，
不能用统一“平台慢”解释，也不需要为它们建立多代升级框架。新旧 DLL 同 SHA
却出现不同 App Control 结果仍保留为环境调查事实：先后路径/链接方式对照
不一致，不能把后续 MAPS 连通或一次导入成功写成已证明的修复。

## 2026-10-16 并行实机复盘

并行增加了覆盖，也暴露了测试工具本身的缺口。产品错误、环境错误和验收
脚本错误必须各自闭环；不能把控制器正常退出或后一次成功覆盖前一次失败。
当前确认的修复均围绕已有责任边界，没有恢复多代兼容框架。

| 现象 | 已确认原因 | 修复与证据边界 |
| --- | --- | --- |
| Windows 安装返回后文件仍被占用 | 把 Windows 的 `os.exec*` 当作 POSIX 同 PID 接管，外层先返回、内层仍运行 | 两适配器沿用已有 owned Job，显式传递标准流并等待实际退出码；Windows Codex 4 项、CC 2 项回归通过。后续真实 Codex 冷准备 33.844 秒、64 个安装文件匹配，原 WinError 32 未再现 |
| Windows 合法服务被报 `foreign_task` | Scheduler COM 返回裸用户名，与计算机名相同时，账号查询得到域 SID；任务 XML、TokenUser 和保存记录原本一致 | Core `e1d1bd6` 从同一任务 XML 的唯一 Principal/UserId 读取 SID，由 Win32 解析；删除裸名查询，保留严格所有权验证。原未启动任务只读核对及精确退役通过；全新服务 2.047 秒就绪、消费锁持有及正常退役通过，零模型 |
| Codex 更新后旧进程中的新 thread 不执行 Hook | 原生 app-server 缓存旧插件命令，安装器更新单一信任摘要；旧 thread 成功不能覆盖新 thread | `f0cbc1a` 使用不随版本变化的 Hook 命令解析现有 canonical 绑定及精确 runtime receipt。真实双安装文件匹配，旧 thread、同进程新 thread、新进程均通过；不新增信任列表或第二安装选择器 |
| CC 首次摘要 `native_max_turns` | 实际失败证据只确认轮次耗尽；独立本地协议实验进一步证明 `max-turns=1` 会截断宿主 StructuredOutput 校正；改为两轮后，Mac/WSL 自然摘要仍失败 | `071e077` 删除适配器轮次上限，复用宿主自身的结构化输出校验重试及明确终止；不覆盖原生 retry 设置、不加应用重试或手工 JSON fallback。原生 2.1.269 / 2.1.299 均验证三次非法后第四次成功、连续非法在五次请求后失败；严格 schema 和累计实际用量保留，自然摘要独立验证 |
| WSL 原生初始化退出 129 | 测试启动 shell 退出时取消正在启动的 Claude；同一可执行文件在持续前台连接下正常 | 无产品、无模型实验复现；改为前台 SSH/WSL 等待实际驱动结束后，安装、两个 MCP 及真实查询/正文读取通过。不是产品业务超时 |
| 原生模型请求退避约 175 秒后失败 | 验收误把管理端连接当作模型连接，实际返回 401 | 保留认证失败和原生报告的零用量；测试先只读验证实际模型端点与目标模型。未进入模型业务，不能归因为慢模型或提高期限 |
| Windows 测试服务无法读数据目录 | 管理员 pytest 的受保护临时祖先不允许普通用户读取，后代继承该 ACL | 仅新 fixture 复用已有 TokenUser 私有目录机制；不放宽产品所有权，不修改全局 ACL。单独验证普通用户服务可访问 |
| 原生安装验收等待不存在的事件 | 测试在未发起首个 turn 时等待 SessionStart 完成；另有旧脚本绕过 Hook 信任及保留已退役配置 | 复核实际宿主事件时机与正常信任接口；安装、MCP 就绪和首轮自然 Hook 分别断言。修测试并核对安装字节，不把超长等待变成产品补丁 |
| Lenovo `uv --python 3.13` 报错误 448 | 全局既有 Python junction 和 shim 被系统以不受信任装入点拒绝；精确真实解释器可执行 | 复用标准 `uv python install --install-dir --no-bin --no-registry` 在任务目录准备解释器；新 PowerShell 仅三个 `UV_*` 配置即通过原产品命令。无 PATH、注册表、系统安全或产品变更；旧控制器“无任务级方案”的结论被新证据纠正，原失败保留 |
| WSL Codex 首轮严格动作检查失败 | 模型读取 Skill 时少展开一层已明确声明的目录，实际 `cat` 返回 1；产品路径与宿主别名定义正确 | 原严格失败保留，两份独立只读核对证明额外动作无副作用、query/explain 正文和自然摘要已完成且用量已知；仅续接从未提交的增量，不重放首轮，不扩大通用动作白名单 |
| Windows 切换夹具安装字节不符 | 测试写文件产生 CRLF，Git `autocrlf=input` 在候选归档中规范为 LF，四个文件仅换行不同 | 修正夹具显式写 LF，未修改产品。最终 `00dd20d` 两套原生安装 64 文件均匹配，完整切换 2.822 秒；切换中自然 Stop、旧/新会话查询及精确退役通过 |

CC 的旧 WSL 首次摘要保持失败，已知用量为 2497 input / 651 output，
清理成功，增量未执行；新的小型 Flash 协议验证用量为 1818 / 259。
这两次原生调用不是同一任务的重试，也不能合并为“旧摘要成功”。
后续 `785eacd` 在 Mac 和 WSL 的真实摘要均再次报 `native_max_turns`，
清理正常且未发增量，分别记录为新源码的新合成任务失败。小型协议输入
成功不能覆盖真实采集摘要的输入规模和原生校正过程。
Mac 双运行时实验分别测得 Codex 切换约 0.433 秒、CC 约 0.520 秒，
只说明对应机器、宿主和源码的受控热切换通过，不是六组合业务验收或统一
时延保证。排他锁内的 Stop 已持久入队，恢复停用后取消且零摘要，不能用其
证明摘要和索引。

测试隔离也发生过实际违规：一个外部测试控制器误用适配器配置变量，写入
全局测试授权选择，之后自行删除全局目录。控制器已停止，创建和删除证据
保留；缺少事前不存在证明，不能保证未覆盖原选择，也没有猜测重建选择。
这是测试执行越界，不属于产品自动更新合同。后续任务显式限定独立目录，
逐入口核对配置变量，真实产品选择不得用测试清理覆盖。

### 当前新增问题的归属与处理

2026-10-16，以下条目按真实因果分别处理：

## 已定位的因果链

Codex Windows 的新自然 Hook 对照证明 SessionStart、UserPromptSubmit、
Stop 可以执行，直接 Python 与产品 PowerShell 包装均成功。随后只在
任务自有安装中加诊断，观察到插件 Stop 正常进入原 launcher、授权与
payload 解析通过，采集 helper 在约 164 ms 内失败。原生路径使用
`\\?\` 扩展命名空间，而 profile 比较的另一端没有该前缀；同一文件
被误判越界。这是适配器的路径身份错误，不是宿主缺少 Stop 能力。

进一步逐表核对发现，原始业务回合实际已入队。旧验收脚本只检查
`material_summary_attempts`、streams、tasks、batches，没有检查 captures；
`capture_attempt_count` 实际保存的是摘要尝试数。旧观察结果保留，撤销
其“没有 capture”的解释，修正 snapshot 字段与逐阶段核对。后续路径
拒绝与原始 queued 是不同事件，必须分别分析。原 consumer.lock 记录曾
启动 PID 45044，但退役核对时已不持有锁；没有留下服务退出原因。
原队列不重放，新验收使用独立、更深的数据目录，保留旧数据和费用记录。

独立无模型 fixture 通过真实 Windows Codex 0.162.0-alpha.17.2
app-server 的 thread/start 和 MCP initialize 启动长活 marker，使用原
产品 service spawn 路径；原生宿主退出后 marker 心跳立即停止。进程
查询确认外层 Job 标志为 8192（KILL_ON_JOB_CLOSE），且没有允许
BREAKAWAY 或 SILENT_BREAKAWAY。该 Job 包含 MCP 的宿主祖先链。
这证明适配器自己的 helper 允许脱离，仍不足以跨越宿主所有权边界。
该实验未调用模型、未读取或重放原业务队列；它是机制复现，不是补造
原始事件的退出日志。

因此 Windows 知识服务需要明确独立于短宿主的所有者。当前设计方向为
复用系统 Task Scheduler 的按需服务宿主，不设周期或登录触发，不增加
常驻 broker。现有 consumer lock、认证 endpoint、worker readiness 和
精确 retirement 仍负责实际服务状态；任务登记或 Running 不算就绪。
共享候选已实现这一边界。新无模型实机实验经过真实 Codex app-server、
MCP、bounded helper 和 `cli.ensure_service`，取得认证 endpoint 的
`worker_alive=true`；宿主 exit 0 后仍可认证查询，consumer lock 继续持有。
实验同时用合成环境变量验证 MCP 声明、一次性上下文传输和 worker 初始化
的完整路径。随后精确 retirement 确认任务删除、consumer lock 释放。
这比单独 marker 存活多验证了实际 core 服务，但仍不是材料/索引验收。

同一测试进一步放到 392 字符的 manifest/XML 深路径，先暴露服务启动锁
仍使用普通路径的问题。共享锁、connection、retirement 和启动诊断文件
统一使用已有 Windows I/O 路径工具后，又定位到 Task Scheduler 的
`WorkingDirectory` schema 只允许 260 字符。保持 manifest、XML 和
权威数据目录不变，仅移除非必要的任务工作目录字段，真实服务就绪、
宿主退出后存活和精确退役再次通过。Python host 保留原启动工作目录
语义；不把迁移到短数据目录作为修复，也不把组件路径测试视为已覆盖
系统任务登记约束。

最终源码的另一独立实机 fixture 保留 395 字符 manifest 路径，并检查
服务内 cwd 与调用者一致。真实 Codex exit 0 后，认证 worker 和
consumer lock 均继续有效；一次性 DPAPI 上下文已消费删除，XML 不含
`WorkingDirectory`。精确退役后任务不存在、消费锁释放。它不调用模型，
也不读取原业务队列；仍须以最终安装上的自然 Stop 完成材料/索引验收。

安装配置只持久化选定原生 profile、可执行文件、诊断位置及允许传递的
环境变量名称。Windows 使用绑定 SID、配置指纹和 nonce 的短期 DPAPI
文件传递实际值，服务启动前消费并删除，不把凭据写入 Task XML 或引擎
配置。POSIX 也应用相同的安装路径声明，环境值沿原有继承路径传递。
凭据缺失由实际 provider 校验，关闭贡献时不要求无关的模型凭据。

审查继续区分系统管理 RPC 与服务业务寿命：Task Scheduler 管理请求保留
有限 IPC/输出边界；服务本身没有任意 60 秒总时限。Start 响应不确定时，
一次 idle 状态或未变化的 LastRunTime 不能证明它没执行，不允许据此再次
Start。清理阶段同样不能无限等待不确定的 manager 状态；静态错误阶段、
代码和不确定标记必须穿过 Hook/调用边界，不能再次压成不可定位的通用失败。

共享宿主的独立审查又复现并修正四条边界，保留修复前后证据：

- 调用者未提供某个声明变量时，后台环境中的旧值可能被继续使用。现在
  先按 Windows 名称大小写规则清除声明范围，再应用已验证的调用者值和
  固定路径；缺失仍为缺失，其他环境不变。
- 系统已接受 Start，但写入 `started` 回执失败时，原分支删除待消费的
  上下文并误报确定失败。现在保留启动 intent 和上下文，返回
  `start_receipt_write_failed / uncertain:true`；后续只核对同一 attempt，
  故障注入确认没有第二次 Start。
- Stop 的新启动路径曾锁定 `state-v1/start.lock`，查询和退役使用
  `domain/start.lock`，两把真实锁可同时取得。现在统一到既有共享锁；
  回归持有该锁时要求合并等待，不能调用 manager。
- 同一配置的 `\\?\` 写法在 `Path.resolve` 后仍保留前缀，但启动记录
  曾去掉前缀，改变了既有 fingerprint。Lenovo 只读实验证明它们指向
  同一文件却往返失败；记录现保留调用者 resolved spelling，不改现有
  指纹和退役协议，也不迁移历史状态。

这些修正说明“把服务放到 Scheduler”本身不够：还要保留调用者上下文、
共享互斥和真实操作结果。独立审查未发现额外高置信阻塞，但不替代最终
组件回归与原生材料验收。

CC Windows 使用实际 `d78b628` 的 bounded runner 复现服务归属。
在清理前持有服务真实 PID 的进程句柄：默认路径中服务从存活变为
Job cleanup 后退出；只为明确的服务启动允许脱离后，服务在 cleanup
后仍存活，正常 release 后以 0 退出；普通孙进程仍被 Job 终止。
这证明 Popen 成功不能代表已完成所有权转交。此实验只覆盖自己的
helper Job，严格外层 Job 是进一步发现的边界。它与冷索引耗时是两个
可叠加的问题，不能用其中一个解释掉另一个。

修正后的 Windows 小语料进程级 fixture 已完成两次真实 helper 查询，
耗时分别为 1.339 秒和 0.206 秒。两次使用同一服务 PID、endpoint 身份
哈希及 ReMe 对象；只发生一次 checkpoint load 和 material rebuild，
第二次没有重载或重建。共享 retirement 能停止服务并释放 consumer，
精确 receipt restore 通过。这证明进程所有权修正的效果，尚不能替代
660 条语料或真实 Claude Stop 的验收。

| 后台模型上下文不完整 | Codex 业务模型可用而摘要 worker 未继承选定 provider；CC 原生结构化输出未纳入适配 | 把后台执行当作新默认环境，而没有兑现安装选定的宿主身份和配置 | provider 最小投影、精确 schema 与返回/usage 先保存已实现；macOS 两产品索引通过 |
| 异步链路状态不可直接定位 | Codex 旧 snapshot 将 summary attempts 误称 capture，原回合实际 queued；CC 也有 queued 但无 consumer 结果 | 已安装、命令可解析或入队成功不能解释事件后续在哪个边界停止；验收字段混淆不同阶段 | 按事件逐表核对 capture、材料、index queue 与 model ledger；仅在缺失边界增加有界诊断，不能记录原始私有 transcript 或制造成功回执 |
| 共享契约在适配器内漂移 | 同一 core feed 的 partial、cleanup、receipt 结果在两个 updater 被不同处理 | 适配器保留旧枚举和成功判断，包版本更新没有覆盖实际失败结果 | 修正两端聚合并用同类契约案例验证；完整行保留，业务已完成与次级失败分开报告 |
| 错误处理自身覆盖操作事实 | CC 新候选的 unknown outcome 被 `_record` 失败替换并误做 rollback，rollback 又能以旧状态覆盖新 unknown；晚取消丢掉已收齐的 feed JSON | 业务结果仅附在部分异常或正常返回中，清理/记录/取消分支没有统一保留它 | 独立故障注入已复现三条；将已知操作事实先保留，再报告次级错误，正在修正 |
| 交付与验收环境本身有错误 | fixture 改了 canonical feed 身份；同版本 VCS 安装未自动更新；Windows 测试使用 nul/普通路径匹配 | 测试准备没有始终使用与产品相同的身份和平台契约；部分失败属于 fixture，不应归因产品 | 已逐项修正并回读 bytes/pins；保留产品失败与测试准备失败的区别 |
| 测试定义存在但 CI 未收集 | CC CI 仅运行 unittest discover，本轮函数式 pytest 用例不会被发现，clean runner 也未声明 pytest | 测试文件存在、定向运行和 CI 实际执行被混为一谈 | 修正依赖与统一收集入口，核对原 unittest 类和新增函数均被收集；独立记录收集与执行结果 |

上述分类不意味着存在一个应当重写全部系统的单一根因。需要共用同一
因果证据的路径才一起重构；独立的平台边界和宿主语义分别解决。

## 已确认的测试盲区

### 服务就绪、实际检索和完整清理是不同边界

共享 Scheduler 的无模型存活实验验证了认证 endpoint、worker、锁和退役，
但没有加载 ReMe。随后 CC Windows CI 的真实 helper 查询暴露
`pythonw -I` 将 stdout/stderr 设为空，ReMe 的 Loguru 初始化不能接受
空 sink。独立原生 fixture 重现相同 TypeError，证明这是产品启动边界，
不是仅靠补齐测试上下文可以解决的故障。

`fadee35` 在业务 import 前仅为缺失标准流提供真实 DEVNULL 句柄，
保留已有流及结构化错误，不修改第三方依赖。新的 Lenovo 真实查询分别
用时 10.037 秒和 0.243 秒，复用同一服务与索引，只加载 checkpoint 和
重建材料各一次，返回同一非空引用；精确退役后任务不存在、消费锁释放。
此合成单材料实验没有模型调用，不能替代 660 条语料或自然 Stop 验收。
首次隔离测试环境另有 pywin32.pth 未被递归加载的配置错误，已单独保留，
没有把它混作产品依赖缺失。

原始 TypeError 的阶段还曾被外层 ServiceHostError 改写成通用错误。
修正把同一启动 attempt 的安全阶段、异常类型和原因传到调用方，不读取
可能属于旧 attempt 的 latest 文件，也不传输原始错误文本或私有内容。

Mac Codex `52966a9` 的新自然验收完成 query/explain、两个业务回合、
首次和增量采集、两次索引以及本地发布；两次摘要用量分别为
11237/375 和 11067/256 input/output tokens。第二次记录了
`temporary-profile-cleanup` 故障，故该次验收为 partial，服务已精确退役，
不写完整通过回执，也不重放任何已付费回合。原 errno/path 没有留存，
因果分析以明确代码顺序和可重复的进程级实验为依据。

Codex 为保证结果先记账，有意在 native terminal 后把完整树清理留给
core，但 adapter 随即删除临时 profile。CC 已先回收直接 native 子进程，
仍可能有继承同一进程组的孙进程写文件。因此共同修正为现有 core owner
创建私有 scratch：先持久化结果/用量，再终止完整树与管道，最后删除自己
创建的目录；adapter 不回传任意删除路径，也不建立另一套持久状态。
正常、取消与异常共用该边界；清理失败不能覆盖已知结果或诱导重做。

首次 Windows scratch 回归又发现 venv launcher 是实际解释器的中间父进程，
严格的 direct-parent PID 判断错误拒绝合法 worker。无模型实验已核对
Popen 返回 PID 正好等于解释器的父 PID，而 core PID 是上一级。
修正复用现有 Windows Job 的精确身份验证成员关系；不放宽为任意祖先，
也不新增服务所有者。共享修正 `b18a676` 的 Mac 相关选集为 48 passed、
9 Windows skips；Lenovo 为 20 passed，新增 foreign Job 与命名冲突
两例另有 2 passed。真实写入者在结果回调时仍活着，回收后整个树与
scratch 目录均消失。Codex 适配相关选集为 52 passed、31 subtests，
CC 为 Mac 33 passed、6 subtests，Windows 31 passed、6 subtests、
2 POSIX skips。均为无模型回归，不能替代新固定依赖上的原生摘要验收。

### 深路径验收不得悄悄扩大产品范围

已有 Lenovo 文档已经区分：正常 Git 仓库根下的 422 字符数据库、
390 字符 staging、281 字符正文、304 字符发布文件通过；Git 仓库根本身
达到 334 字符仍不受当前依赖支持。新验收 fixture 却把“保留深路径”
写成整个 DATA 根必须超过 260 字符，造成另一次不可用 feed。
这是验收约束扩大，不能当作原路径修复回归，也不能通过改短路径
宣称支持了原来不支持的 Git 根。

该失败保留在独立 profile，未调用模型。只读与本地 bare 对照分别确认
绝对 Git 根、扩展命名空间及深工作目录的依赖限制；`core.longpaths`
不消除这些边界。后续原生验收采用依赖支持的 Git 根，同时继续覆盖真实
深材料路径和扩展路径身份；transcript 是否超长按实际路径单独记录，
不把材料的长度当作 transcript 的证据。产品应在适用 Git 边界清楚报错，
不自动迁移数据或建立长期短路径别名。

`3851f58` 在共享 Git 边界增加只读 preflight：当前 Windows Git 的
实际 gitdir 限制为 220 UTF-8 bytes，工作树计入 `.git`，不是所有文件
路径统一限制为 220 字符。Feed 在创建缓存前检查，publication 在
clone/fetch 前检查；两个适配器在打开 Store 前调用同一检查。错误只带
安全 code、角色和长度，不输出私有路径。已有 unknown 发布的对账若被
该配置限制阻止，仍保留 unknown、head、PR 及已完成 push 步骤，不会
变成 not_started 并重发。Mac 22 项、Lenovo 14 项组件回归通过，
两端 prepare-store 入口各通过；全部八个相关文件与 Windows 测试清单
逐字节一致。最终安装验收尚待进行。

### Stop 管理开销与测试源码漂移

Codex `52966a9` 的 Windows CI 出现 12 errors、1 failure，均位于
Stop 的 3/5/8 秒前台观察期限。独立合成 Stop 使用同一共享启动路径，
收到 `accepted-local` 和 wake requested，但总计 6.966 秒：ACL 检查
0.413 秒、SID 查询 0.329 秒、两次任务查询 2.986/2.173 秒、登记
0.498 秒、Start 0.483 秒。两次查询占约 74% 的总耗时。这既不是推理
超时，也不是先前 ReMe 缺标准流；它说明短测试期限确实覆盖不了当前
启动管理成本，仍须先解决可消除工作。

按确切名称的 COM 读取实测约 0.38–0.45 秒，CIM 查询约 2.04–2.84 秒。
候选只替换查询并复用 ACL 验证返回的 SID，登记、Start、删除保留原路径。
同一合成任务的 never-run、running、finished 三阶段中，SID、State、
LastRunTime、LastResult 已逐项比较一致；COM XML 省略的默认 RunLevel
只能在有效 COM enum 证明其值时补齐，不能绕过原有归属校验。首次投影
因此被拒绝的失败记录保留，测试任务均精确删除。相关选集为 Mac
75 passed、2 Windows skips，Lenovo 77 passed；含 accepted Start
后的记账失败与 unknown 不重放路径。独立 review 未发现新阻塞。

同脚本、新隔离状态的优化后 Stop 为 3.116 秒，两次查询合计
1.572 秒，前台总耗时下降约 55%。本次第一次 COM 查询仍用时
1.160 秒，不能把先前 0.38–0.45 秒的读取微测推广成每次冷启动承诺。
若测试要验证“完整 JSON 不等待 stdin EOF”，就不应把系统服务冷启动
也塞入其 elapsed < 2 秒断言。输入/队列/授权用例将明确隔离 wake
传输，保留真实 helper、持久准入及既有 Engine 消费断言；真实 Scheduler
启动、归属、消费、退役继续由独立实机门槛负责。最终 CI 尚待验证。

对应 Codex 测试修正为 `6110afb`：Mac 在正式 `8104082` 运行时上
18 passed、4 subtests；Lenovo 首次 17 passed，另一个案例业务断言均
通过但 teardown 遇 WinError 145。只读检查发现普通临时目录下仍有

两次运行拼成一次全绿。真实 helper、准入、capture 与 Engine 消费未被
模拟；只替换明确的 wake 传输并验证请求或拒绝。没有放宽既有期限。

`6bc2c9e` 的回归通过一个延迟 5.25 秒的本地 HTTP 服务，直接调用

CC 曾用原生 `num_turns > 1` 判断额外模型调用；旧测试同样构造该字段并

后续测试应验证边界对外的行为与副作用，不能仅断言传入 `timeout=None`
或模拟函数被调用。原生事件、进程树归属、业务结果、索引持久状态及费用
回执需要分别检查。组件与进程级测试负责稳定复现；少量真实宿主调用验证
实际协议，不以反复付费运行代替可定位的回归。

更新事务的交叉审查还发现同类问题：两个适配器均需要把原生操作事实与
状态文件写入结果分开。已有 journal/receipt 保持为事务权威，原生写入前
保存 intent；响应错误后只读核对精确版本、选中状态及包字节。已验证的
安装可完成本地提交，不应再次执行安装；结果 unknown 时保留 journal，
后续普通检查可继续只读核对，不能自动回滚或重放。单次目录快照与旧值
相同，也只有在原执行及其子树已确认终止后，才能证明没有未决写入。
已完成 feed 的完整结果即使遇到晚取消、记录失败或清理失败也须保留，
并分别报告未完成部分。这些规则由故障注入验证，不能只依赖成功路径。

独立上下文审查还发现：已固定的原生 profile 可能被 updater 的环境覆盖，
以及 prepared 元数据中的另一份上下文可能与已校验的 MCP 包声明不同。
CC 升级现保留原有安装路径、只更新代际 adapter 路径；Codex 从已校验
插件包中的 MCP 声明提取服务上下文，事务恢复先核对一致再发布配置，
没有新增一份配置权威。缺失 provider 凭据或路由不在关闭贡献的声明阶段
触发模型验证，实际 summary 仍明确拒绝不可用路由，不借用其他 provider。

产品断言。`42d965c` 只为三处源码 fixture 明确 UTF-8；原失败两项定向

settings.env 高于调用者的优先级；未配置时不探测、安装或伪造 Git Bash。

选择，不增加关闭贡献时的安装依赖。

## 重构决定的依据

- 若耗时来自每次请求重新载入或构建完整语料，修正初始化和增量边界；
  不通过放大超时掩盖重复工作。
- 若耗时来自锁或 owner 生命周期错误，修正所有权、启动与取消传播；
  不启动第二个服务或增加自动重试绕过。
- 若工作本身持续推进且成本与材料量相符，修正任意业务总时限，
  同时保留调用者取消、连接故障和具体资源边界。
- 若宿主未派发或没有执行 Hook，修正宿主契约或安装适配；
  若命令已执行而后续丢失，修正对应解析、身份、授权或持久准入阶段。
  不用手动注入 Stop 宣称原生链路通过。
- 如果相同生命周期或平台规则由多个组件各自实现并已产生不同语义，
  优先收敛到其现有责任方。是否抽取共享实现由实际重复和依赖方向决定，
  不新增通用编排层、第二权威状态或日常用户操作。
