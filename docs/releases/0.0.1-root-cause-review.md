# 0.0.1 发布问题根因分析

状态：调查中，2026-10-15。本文记录确认的因果与待验证假设，不代表
发布通过。候选、平台矩阵及证据边界见 [0.0.1](0.0.1.md)。

## 判断标准

用户要求妥善解决发布中暴露的问题，允许必要的重构和设计调整。总耗时
不是降低质量要求的依据。分析区分四层：

1. 现象：用户实际得到的结果、失效阶段和数据影响。
2. 直接原因：以具体调用、事件、源码和回执说明如何造成该现象。
3. 系统原因：为什么设计、职责划分、测试或交付机制没有提前阻止它。
4. 闭环：修复原因、相邻同类路径、验证实际产品行为并保留原失败证据。

单次运行超过 60 秒只证明耗时超过阈值。它不能证明业务合理地需要这么
久，也不能证明死锁。提高或取消阈值与消除低效、等待或生命周期故障
是不同工作，分别提供依据。

移除两个外层 60 秒限制的 CC 提交 `a909eb1` 当前仅是未推送的候选方案。
其定向测试证明了结果交付和取消透传，不证明超时根因已经解决。
调查还覆盖 updater 的 `FEED_BUDGET=60`，不能修 setup 后遗漏同一业务
操作的更新入口。锁等待、连接、清理与调用者要求的截止时间独立分类，
不统一删除所有 timeout。

## 已定位的因果链

Codex Windows 的新自然 Hook 对照证明 SessionStart、UserPromptSubmit、
Stop 可以执行，直接 Python 与产品 PowerShell 包装均成功。随后只在
任务自有安装中加诊断，观察到插件 Stop 正常进入原 launcher、授权与
payload 解析通过，采集 helper 在约 164 ms 内失败。原生路径使用
`\\?\` 扩展命名空间，而 profile 比较的另一端没有该前缀；同一文件
被误判越界。这是适配器的路径身份错误，不是宿主缺少 Stop 能力。

进一步逐表核对发现，原始业务回合实际已入队。旧验收脚本只检查
`material_summary_attempts`、streams、tasks、batches，没有检查 captures；
`capture_attempt_count` 实际保存的是摘要尝试数。旧观察结果保留，撤销
其“没有 capture”的解释，修正 snapshot 字段与逐阶段核对。后续路径
拒绝与原始 queued 是不同事件，必须分别分析。原 consumer.lock 记录曾
启动 PID 45044，但退役核对时已不持有锁；没有留下服务退出原因。
原队列不重放，新验收使用独立、更深的数据目录，保留旧数据和费用记录。

独立无模型 fixture 通过真实 Windows Codex 0.162.0-alpha.17.2
app-server 的 thread/start 和 MCP initialize 启动长活 marker，使用原
产品 service spawn 路径；原生宿主退出后 marker 心跳立即停止。进程
查询确认外层 Job 标志为 8192（KILL_ON_JOB_CLOSE），且没有允许
BREAKAWAY 或 SILENT_BREAKAWAY。该 Job 包含 MCP 的宿主祖先链。
这证明适配器自己的 helper 允许脱离，仍不足以跨越宿主所有权边界。
该实验未调用模型、未读取或重放原业务队列；它是机制复现，不是补造
原始事件的退出日志。

因此 Windows 知识服务需要明确独立于短宿主的所有者。当前设计方向为
复用系统 Task Scheduler 的按需服务宿主，不设周期或登录触发，不增加
常驻 broker。现有 consumer lock、认证 endpoint、worker readiness 和
精确 retirement 仍负责实际服务状态；任务登记或 Running 不算就绪。
服务上下文、凭据来源、启动结果不确定及 exact-owner 清理仍在设计审查，
没有把这个方案写成已实现或已验收。

CC Windows 使用实际 `d78b628` 的 bounded runner 复现服务归属。
在清理前持有服务真实 PID 的进程句柄：默认路径中服务从存活变为
Job cleanup 后退出；只为明确的服务启动允许脱离后，服务在 cleanup
后仍存活，正常 release 后以 0 退出；普通孙进程仍被 Job 终止。
这证明 Popen 成功不能代表已完成所有权转交。此实验只覆盖自己的
helper Job，严格外层 Job 是进一步发现的边界。它与冷索引耗时是两个
可叠加的问题，不能用其中一个解释掉另一个。

修正后的 Windows 小语料进程级 fixture 已完成两次真实 helper 查询，
耗时分别为 1.339 秒和 0.206 秒。两次使用同一服务 PID、endpoint 身份
哈希及 ReMe 对象；只发生一次 checkpoint load 和 material rebuild，
第二次没有重载或重建。共享 retirement 能停止服务并释放 consumer，
精确 receipt restore 通过。这证明进程所有权修正的效果，尚不能替代
660 条语料或真实 Claude Stop 的验收。

### 同语料的耗时分解

下表来自隔离无模型诊断，使用相同公开提交的 660 条语料与既定运行时。
包含采样/计时包装开销，且机器硬件不同；不是 OS 单变量 benchmark。
后文补充已完成的无采样对照，最终安装路径仍待验证。

| 操作 | macOS wall | Windows wall | Windows 已定位成本 |
| --- | --- | --- | --- |
| 首次同步 | 9.275 s | 113.736 s | CPU 96.891 s；三轮包校验约 56.50 s，文件提交和元数据操作显著；锁等待约 4.5 ms |
| 首次查询 | 15.554 s | 132.278 s | CPU 118.891 s；ReMe apply_changes 124.075 s，含 checkpoint commit 11.214 s |
| 热查询 | 0.928 s | 8.026 s | CPU 7.047 s；仍需区分检索/排序/分组成本与诊断开销 |

完整包校验原先依次发生在 Feed、Store.install_feed 和
MaterialStore.install_packages，后两层中的一层只为了取得已验证的
entry headers。共享候选已将完整校验收敛到实际安装边界，向上返回已验证的
metadata；目录身份、ready 门槛、坏末尾原子性与每次源文件读取的哈希/
路径检查继续保留。不建立可信布尔开关或持久化第二套正文。

进一步分解的一次冷查询中，ReMe 共 131.146 秒，逐块 upsert 累计
51.844 秒，其中 posting 扩展为 37.290 秒；chunker 累计 34.134 秒，
checkpoint 为 10.772 秒。这些嵌套计时不能直接相加。全局 doc 数组追加
仅 0.222 秒，不能把它误报为主因。候选直接使用 ReMe 已有 batch upsert，
保留相同分词、切块、排序和正文校验；故障后的 checkpoint 恢复继续验证。

关闭上述函数级采样后的同机、同公开提交、相同运行时对照如下。baseline
和两项优化候选顺序运行，各用独立 fresh root，不包含付费模型调用。

| 操作 | baseline wall / CPU | 两项优化候选 wall / CPU |
| --- | --- | --- |
| 首次同步 | 114.366 / 96.391 s | 68.478 / 57.094 s |
| 首次查询 | 135.082 / 121.578 s | 100.415 / 90.391 s |
| 热查询 | 8.315 / 6.516 s | 8.155 / 6.281 s |

同步和首次查询 wall 分别下降约 40.1% 和 25.7%。这是一组根因修正对照，
不能推广为所有任务的性能承诺。两次查询的完整返回对象逐字段一致，
包含顺序、得分、引用及正文摘录；同步回执的时间字段自然不同。候选仍
超过 60 秒，因此减少已确认的重复工作和修正任意业务总时限都需要完成。

热查询时间几乎不变，定向计时已确认原因：在总耗时 7.643 秒的一次查询中，
2300 个匹配 chunk 重新计算 `body_tokens`，累计 6.605 秒，占 wall 的
86.4%。它没有重建索引，checkpoint generation 保持为 1。

第一版内存词集复用使热查询降到 0.857 秒，完整结果不变，但新增
2300 个 frozenset 与 token 对象估算约 153.77 MB。这不是可忽略代价，
该表示不作为最终方案提交。后续候选改为有序 tuple、索引内共享字符串
及精确二分查找，保留未变 chunk，淘汰删除/替换 chunk 的派生缓存。
不新增正文副本或持久化格式。最终 Lenovo 定向热查询为 0.732 秒，
CPU 0.609 秒，重复 `body_tokens` 调用为 0，完整结果与前述对照一致。
tuple、局部词池及共享字符串合计估算 24,860,402 bytes，约 24.86 MB，
比被弃用的 frozenset 表示减少 83.8%；这不是进程 RSS。淘汰一个派生
缓存 chunk 并整理词池约 0.282 秒，未改写权威正文或 checkpoint。
新进程加载已有 checkpoint 并首次查询仍需 20.890 秒，不能用热查询
掩盖首次计算成本。

这些路径和性能变更已合入共享候选
`fe7e1a0cf927133fb0c75c46f8cc235a7abf2ab8`。最终 ReMe 相关选择在
macOS、Lenovo 各 51 项通过；联合新增回归为 18 passed、3 Windows
skips、3 subtests passed。安装的产品尚未切换到该候选，服务宿主修正
完成后再固定两端依赖和验证实际安装。

不直接复用 BM25 词典编号代替正文词集：正文先移除引用，可能产生原
词典没有的合法独立 token，例如引用后相邻的 `:x`。缺词不能被静默忽略，
也不能误报材料损坏；此语义边界加入回归。

| 类别 | 具体证据 | 系统性缺口 | 修正方向与状态 |
| --- | --- | --- | --- |
| 跨层操作寿命合同不一致 | CC RPC 5 秒、launcher 60 秒、setup/feed 60 秒；`6bc2c9e` 只修 RPC，外层仍截断 | 架构声明无默认业务总时限，但入口、进程包装与服务分别定义总时限；局部回归没有穿过真实入口 | 绘制一次操作完整调用链及各期限归属，结合实测决定修正；调查中 |
| 宿主协议假设未经实际验证 | CC 顶层 oneOf 工具不可见；摘要未传精确 schema；num_turns 被误认成模型次数；Codex 启动提示被判禁止事件 | 模拟输入与实现共享同一错误假设，组件测试不能验证宿主真实行为 | 已修具体契约并有 macOS 实证；需要固定目标宿主版本的真实适配回归 |

| 错误处理自身覆盖操作事实 | CC 新候选的 unknown outcome 被 `_record` 失败替换并误做 rollback，rollback 又能以旧状态覆盖新 unknown；晚取消丢掉已收齐的 feed JSON | 业务结果仅附在部分异常或正常返回中，清理/记录/取消分支没有统一保留它 | 独立故障注入已复现三条；将已知操作事实先保留，再报告次级错误，正在修正 |

上述分类不意味着存在一个应当重写全部系统的单一根因。需要共用同一
因果证据的路径才一起重构；独立的平台边界和宿主语义分别解决。

## 已确认的测试盲区

`6bc2c9e` 的回归通过一个延迟 5.25 秒的本地 HTTP 服务，直接调用
`mcp_server.knowledge_call`。它正确验证了 RPC 不再被 5 秒截断，但没有
经过原生 MCP launcher，因此没有覆盖外层 60 秒。这是测试范围不足，
不是该回归本身无效。

CC 曾用原生 `num_turns > 1` 判断额外模型调用；旧测试同样构造该字段并
断言拒绝。实际结构化输出的工具结果事件也会递增计数，说明该测试只保护
了实现假设。`d78b628` 已纠正推断，保留原生模型调用上限、严格 schema、
错误结果和第二次 invoke 的保护。

后续测试应验证边界对外的行为与副作用，不能仅断言传入 `timeout=None`
或模拟函数被调用。原生事件、进程树归属、业务结果、索引持久状态及费用
回执需要分别检查。组件与进程级测试负责稳定复现；少量真实宿主调用验证
实际协议，不以反复付费运行代替可定位的回归。

## 重构决定的依据

- 若耗时来自每次请求重新载入或构建完整语料，修正初始化和增量边界；
  不通过放大超时掩盖重复工作。
- 若耗时来自锁或 owner 生命周期错误，修正所有权、启动与取消传播；
  不启动第二个服务或增加自动重试绕过。
- 若工作本身持续推进且成本与材料量相符，修正任意业务总时限，
  同时保留调用者取消、连接故障和具体资源边界。
- 若宿主未派发或没有执行 Hook，修正宿主契约或安装适配；
  若命令已执行而后续丢失，修正对应解析、身份、授权或持久准入阶段。
  不用手动注入 Stop 宣称原生链路通过。
- 如果相同生命周期或平台规则由多个组件各自实现并已产生不同语义，
  优先收敛到其现有责任方。是否抽取共享实现由实际重复和依赖方向决定，
  不新增通用编排层、第二权威状态或日常用户操作。

每个核心问题的最终记录包含触发条件、源码及宿主版本、根因证据、
涉及路径、修正与回归、实机结果、剩余限制。旧 paid/unknown 回执保留，
新验证使用独立标识；对既有不确定外部副作用先核对再决定后续操作。
普通读取的无模型诊断复现与付费模型/公开写入分别记录。

benchmark 的组件收益与版本收益仍独立推进；本次为排错开展的耗时分解
属于正确性与首用性能诊断，不等同于完成 benchmark。
问题根因、代码修复、组件测试、原生验收和正式 Release 分别完成后记录。
